# LocaleLens

**地区数据观察站。** 持续、全量、留档地记录一个地区正在发生什么，让"别人看今天一张截图，你已经记了一年"成立。

当前观察对象：**杭州**。

---

## 给 AI 的导航（先读这里）

如果你是一个要在这个仓库里工作的 AI，按以下顺序读：

1. **`README.md`**（本文件）— 项目是什么、数据在哪、怎么跑
2. **`SCHEMA.md`** — 每个字段的含义与口径，**不要猜字段**
3. **`config/sources.yaml`** — 有哪些源、抓什么、多久抓
4. **`digest/daily/YYYY-MM-DD.md`** — 想要"今天发生了什么"，直接读这里，**不要扫 JSONL**
5. **`data/<source_id>/<dataset>/YYYY-MM-DD.jsonl`** — 要精确数值时才读

**重要**：`raw/`、`data/`、`derived/`、`digest/`、`health/` 全部不进 git，只存在于本地。

## 三层留存（核心设计）

"不知道未来哪些数据有用"的唯一正确解：**存原始，不存结论。**

| 层 | 位置 | 内容 | 可变性 |
|---|---|---|---|
| **L0 原始快照** | `raw/<source>/<dataset>/YYYY/MM/DD/HHMMSS.html.gz` | 完整页面，压缩归档 | **只增不改** |
| **L1 规范化** | `data/<source>/<dataset>/YYYY-MM-DD.jsonl` | 最小必要字段，一行一条事实 | 当天可重跑覆盖 |
| **L2 派生** | `derived/` | 同比、环比、去化、分化度 | 随时从 L1 重算 |

**为什么必须存 L0**：未来想加一个新指标时，可以用新解析器重跑历史快照回填。若只存 L1，历史永久丢失。

## 设计原则（改动前请先读）

1. **文件即真相。** 不装数据库。需要 SQL 时用 DuckDB 只读查询 JSONL，不产生第二份数据。
2. **原始层只增不改。** 规范化可以重跑，快照不行。
3. **每个源独立可失效。** 一个源坏了，不能让它伪装成"系统正常"。
4. **不做评分、不做预测。** 只记录、对比、暴露异常和缺口。
5. **礼貌抓取。** 低频、节流、标注来源、不商用、不转售。
6. **缺失就标缺失。** 不允许用旧数据冒充满新数据；过期要在 digest 里明说。

## 口径变更检测

这是本项目最重要的一项自动检查。原理：

```
implied_prev = 本期值 / (1 + 公布增速/100)
```

用 `implied_prev` 和库里存的「上年实值」比对，差异 ≥ 2% 就判定该年数据被修订过。

**为什么必须有**：杭州社零 2023 年公布 7,671 亿，2024 年公布 9,151 亿。
看起来一年涨 19%，但 2024 年公报写的是「比上年增长 2.8%」——
反推 2023 年基数约 8,902 亿，说明第五次全国经济普查修订了 2023 年数据。
不校验就会得出完全错误的结论。

```bash
uv run locale-lens check     # 单独跑检查
```

结果写入 `derived/checks/<日期>.jsonl`，并出现在日报第六节。

## 高德 POI 的坑：count 会封顶

高德 `place/polygon` 的 `count` 字段**不是真实总数**：结果过多时会被截断成
**600 或 1000**（不固定）。实测「上城区便利店」和「淳安县便利店」都返回 600。

如果不识别这一点，会得到一张「所有区县门店数都一样」的假表。

解决办法是**自适应网格**：

1. 先按区县 bbox 查一次
2. `count` 命中 600/1000 → 把 bbox 切两半（切长边，短边切了没用）分别查
3. 递归到全部低于封顶值，或切到最小格（约 1.5 km）
4. 最小格仍封顶 → 该格记为**未知**，绝不把封顶值当真实值

代价是调用量大：13 区县 × 4 类别，约 6 分钟 / 1500 次请求。所以 POI 设成**每周一次**。

当前结果：52 项里 8 项未知（15%）。咖啡厅、购物中心全部可信；餐饮和便利店在密集城区仍拆不到底。

**口径边界**：这是高德 POI 库里的门店存量，不是工商注册数、不是实际营业数，
更不是客流或营收。只能做同类门店的区县横向对比与自身趋势。

## 采集频率（重要）

**频率应该匹配数据真实的发布节奏，而不是站点自称的刷新频率。**

实测证据：
- 透明售房网声称「每小时统计一次」，但 13:00/14:00/15:00/16:00 四次采样只有 15:00 变过一次，
  16:47 复查与 16:00 完全一致 —— 实际一天只更新一两次。
- 「当日成交」是**累计计数器，每天清零**。一天里只有最后一次抓取有意义，
  而「今日」页面第二天就没了 —— **日终值当天不取，永久丢失**。
- 库存是**存量**，一天变动 11 套（39,000 套里），日内高频采样无意义。

| 源 | 频率 | `min_interval_hours` | 依据 |
|---|---|---:|---|
| 交易动态（可售+成交） | 3 次/天（10:00 / 23:30 / 23:55） | 0 | 日终值不可回溯；23:30 与 23:55 互为保险（同为 T23:00 时点，后跑的覆盖前面的） |
| 预售审批公告 | 1 次/天（10:00） | 20 | 事件流约 20 条/天，页面留 8 页≈1 周历史 |
| 解除合同公示 | 1 次/天（10:00） | 20 | 同上 |
| 杭州市统计局 | 1 次/周 | 144 | 月报按月、公报/年鉴按年发布 |
| 数据开放平台 | 1 次/周 | 144 | 新数据集上架以周计 |
| 高德 POI | 1 次/月 | 660 | 门店存量以月为单位变化；单次约 1500 请求、6 分钟 |

效果：每天请求数约 28 次 → **5 次**；每天快照约 30 个 → **9 个**。

**为什么 23:30 和 23:55 都要跑**：当日成交过了零点就没了，一次失败 = 当天数据永久缺失。
两次抓取落在同一个小时（都是 T23:00 时点），正常时后一次覆盖前一次，等于免费多拿一次重试。

低频不是为了省磁盘（快照平均才 8.8 KB），而是**降低被封的风险**——
一旦源站封禁，整个项目就断粮了。

## 定时任务

用 macOS launchd，不是 cron。

```bash
# 查看状态
launchctl list | grep localelens

# 立即手动跑一次
bash scripts/collect.sh

# 卸载
launchctl unload ~/Library/LaunchAgents/com.localelens.collect.plist
rm ~/Library/LaunchAgents/com.localelens.collect.plist
```

日志在 `logs/collect.log`。每天 4 次，一年原始快照约 50 MB。

## 踩过的坑（改代码前必读）

| 问题 | 现象 | 解决 |
|---|---|---|
| WAF 拦 TLS 指纹 | httpx 全部 405，curl 正常 200 | 传输层走 curl 子进程，httpx 仅作回退 |
| 页面不是标准表格 | `<table>` 只有 1 个，其他区块是 `div` | 同时支持 `div.dynamicTable` 与 `table` 两种结构 |
| 行类名不统一 | `mytableLine` vs `myFivetableLine` | 用 `contains(@class,'tableLine')` 匹配 |
| 表头列数 ≠ 行数 | 批准预售表头 6 列、行只有 3 列 | 按 `len(header)//len(row)` 拆成子块 |
| 表单分页无效 | POST 的 `page` 字段被忽略，翻页全是第 1 页 | 分页必须走 GET `?page=N` |
| 政府站列表是 JS 渲染 | 页面只有 7KB，没有文章列表 | 挖出 jpaas 接口 `/api-gateway/jpaas-publish-server/front/page/build/unit`，GET 返回 JSON |
| 连续下载被限流 | 返回 HTML 提示页而不是 PDF（前几字节是 `<div>访问`） | 校验 `%PDF` magic，非 PDF 就退避重试 |
| **覆盖导致归档丢失** | 重跑时跳过下载，新记录把旧记录的 `pdf_path` 抹掉，下一轮又重下 | 跳过下载时必须**沿用上一轮**的附件字段 |
| 空转被当成失败 | 公报都提取完了，返回 0 条 → 健康度记成失败 | 用 `NothingToDo` 区分「无新增」和「解析失败」 |
| 旧文章附件是直链 | `/cms_files/...pdf`，不走 `document/download` | 两种附件形式都要认 |
